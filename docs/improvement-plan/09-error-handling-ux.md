# Шаг 9: Разрозненная обработка ошибок

## Проблема

В проекте нет единого паттерна обработки ошибок:

- Часть мутаций оборачивается в `try/catch` + `toast.error(...)` прямо в
  компоненте (например, `checkout/page.tsx:101-104`).
- Часть полагается на состояние react-query (`isError`) без явной обработки —
  если компонент забыл проверить `isError`, ошибка молча проглатывается.
- Серверные API-роуты (`app/api/email/route.ts`, `app/api/telegram/route.ts`)
  логируют ошибку через `console.error(...)`, что в проде (Vercel) уйдёт в
  логи функции, но никуда не агрегируется (нет Sentry/аналога) — то есть
  продавец/разработчик узнает о сбое уведомления только если сам пойдёт
  смотреть логи.
- "Fire & forget" запросы в `checkout/page.tsx:155-176,181-200` (Telegram/
  email уведомления) гасят ошибку через `.catch(() => {})` — если
  уведомление не доставлено, никто никогда не узнает.

## Почему это важно

Непредсказуемая обработка ошибок означает, что часть сбоев для пользователя
выглядит как "зависание"/тишина, а часть разработчику не видна вообще
(особенно "fire & forget" уведомления продавцу о заказе — если Telegram API
изменится и сломается, продавец просто перестанет получать уведомления о
заказах, и никто не узнает, пока продавец сам не заметит).

## Что сделать

1. Завести единый хелпер для мутаций, который везде одинаково матчит
   ошибку Supabase (`PostgrestError`) в человекочитаемое сообщение и шлёт
   `toast.error`, вместо того чтобы каждый компонент сам решал это
   (`lib/helpers.ts` уже есть — добавить туда `getErrorMessage(error)` и
   использовать во всех `catch`).
2. Подключить error-tracking сервис (Sentry — самый стандартный выбор для
   Next.js + Vercel) хотя бы для server-side ошибок (API routes,
   server actions) — это закроет проблему "тихих" сбоев в
   Telegram/email-уведомлениях.
3. Для "fire & forget" уведомлений — не убирать асинхронность (это
   правильно, не блокировать оформление заказа на уведомлении), но
   логировать неудачу через Sentry/аналог, чтобы это было видно
   разработчику/продавцу, а не теряться в `.catch(() => {})`.
4. Добавить React error boundary на уровне `app/dashboard/layout.tsx` и
   `app/store/[slug]/layout.tsx`, чтобы необработанное исключение в одном
   виджете (например, в графике аналитики) не убивало всю страницу белым
   экраном.

## Критерий готовности (DoD)

- [ ] Единый `getErrorMessage()` используется во всех `catch`-блоках мутаций.
- [ ] Подключён error-tracking, серверные ошибки видны без захода по SSH/в
      логи Vercel.
- [ ] Сбой отправки Telegram/email уведомления логируется и виден
      разработчику.
- [ ] Есть error boundary хотя бы на уровне layout дашборда и витрины.
