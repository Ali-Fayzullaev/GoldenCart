# Шаг 5: Согласовать auth и закрыть дашборд по роли

## Проблема

1. **Несогласованный паттерн сессии.** Коммит `6fb83bb` перевёл почти все
   хуки с `supabase.auth.getUser()` (валидирует JWT на сервере Supabase) на
   `supabase.auth.getSession()` (читает то, что лежит локально, без
   ревалидации) — ради скорости. Но это сделано не везде:
   `app/api/import/route.ts` всё ещё использует `getUser()`. Два разных
   паттерна аутентификации в одном проекте — источник путаницы и
   несогласованного поведения при истёкшей/подменённой сессии.

2. **`middleware.ts` защищает только сам факт логина, не роль.**
   `lib/supabase/middleware.ts:36-47` редиректит на `/login`, если в
   `/dashboard/*` зашёл неавторизованный пользователь — это правильно и
   использует `getUser()` (хорошо). Но дальше **нет проверки `role ===
   'seller'`**. Если в `/dashboard` зайдёт покупатель (`role: 'customer'`),
   его не отфутболят явно — он просто увидит экран "создайте магазин"
   (потому что `useMyStore()` вернёт `null`, т.к. `owner_id` не совпадёт).
   Это не дыра в данных (RLS всё равно не даст ничего прочитать/изменить),
   но это плохой UX: вместо понятного "эта страница не для вас" покупатель
   видит форму создания магазина.

## Почему это важно

Несогласованность auth-паттернов — то место, где наличие двух способов
"одно и то же" рано или поздно приведёт к багу (кто-то скопирует
`getUser()`-версию хука по старому примеру, кто-то — новую, и поведение при
истёкшей сессии будет непредсказуемо отличаться). Слабая проверка роли в
дашборде — не критично с точки зрения безопасности данных, но создаёт
путаницу в UX и осложняет добавление новых ролей в будущем.

## Что сделать

1. Зафиксировать **одно** правило и описать его в `AGENTS.md`/`CLAUDE.md`:
   - в `middleware.ts` и любом server-side коде, отвечающем за допуск к
     защищённым роутам — **всегда `getUser()`** (он валидирует токен на
     сервере Supabase, это единственно правильный выбор для авторизации).
   - в client-side хуках, где идёт речь не об авторизации, а просто о "какой
     юзер сейчас залогинен, чтобы подставить его id в запрос" — можно
     `getSession()`, т.к. реальная защита всё равно идёт через RLS на
     стороне Postgres.
2. Привести `app/api/import/route.ts` к единому правилу (это server-side API
   route, защищающий запись данных — должен использовать `getUser()`).
3. Добавить в `middleware.ts` (или в layout `/dashboard`) проверку роли:
   если `user` есть, но `profiles.role !== 'seller'` — редиректить на
   отдельную страницу/баннер "этот раздел доступен только продавцам", а не
   молча показывать пустой дашборд.
4. Прогрепать остальные API-роуты (`app/api/email`, `app/api/telegram`) на
   предмет отсутствия проверки авторизации/принадлежности магазина перед
   отправкой уведомлений.

## Критерий готовности (DoD)

- [ ] Правило "где `getUser()`, где `getSession()`" зафиксировано в
      `AGENTS.md`.
- [ ] Все server-side роуты используют `getUser()`.
- [ ] Покупатель, зашедший на `/dashboard`, видит явное сообщение о
      нехватке прав, а не пустую форму создания магазина.
- [ ] Все API-роуты, принимающие запись данных, проверяют, что текущий
      пользователь имеет право на это действие (а не только что он залогинен).
