# Шаг 10: Дизайн-система и доступность (accessibility)

## Проблема

1. **Дашборд vs витрина.** В дашборде (`app/dashboard/*`) компоненты
   `shadcn/ui` (Button, Input, Dialog, Table, Badge, Select) используются
   последовательно — это сильная сторона проекта. На витрине
   (`app/store/[slug]/*`) тот же набор компонентов используется вперемешку с
   кастомной Tailwind-вёрсткой (например, `s-card`, `s-border`, `s-text`,
   `s-muted` — судя по `checkout/page.tsx`, это кастомные CSS-классы поверх
   динамических цветов магазина, не часть shadcn). Само по себе это
   нормально (витрина должна быть кастомизируемой под бренд продавца), но
   стоит явно задокументировать границу: "эти классы — для
   бренд-кастомизации витрины, эти компоненты — для UI-механики" — иначе
   новый код будет хаотично мешать оба подхода.

2. **Адаптивность чинилась постфактум.** Как видно из шага 2
   (`_mobile_fix.js`) и коммита `2d9500a`, мобильная вёрстка витрины не
   была заложена сразу, а патчилась позже. Стоит сделать ревизию остальных
   страниц витрины (`cart`, `compare`, `faq`, `profile`) на предмет того же
   класса проблем (фиксированные `flex`/`grid-cols-N` без `sm:`/`lg:`
   модификаторов).

3. **Accessibility:**
   - Кликабельные `<div>` вместо `<button>` (например, в
     `store-layout-client.tsx` шапка магазина) — не работают с клавиатуры,
     не объявляются скринридером как интерактивный элемент.
   - Иконки-кнопки (сердце/корзина/сравнение) без `aria-label` — скринридер
     озвучит просто "кнопка" без понимания, что она делает.
   - Ошибки формы выводятся текстом рядом с полем, но без `aria-describedby`,
     связывающего поле с текстом ошибки — скринридер не прочитает ошибку
     при фокусе на поле.

4. **`card_style` (4 варианта отображения карточки товара)** — хорошая фича
   для кастомизации, но стоит убедиться, что каждый из 4 стилей одинаково
   тестировался на мобильной адаптивности (это легко упустить, если
   адаптивность правилась точечно для одного стиля через `_mobile_fix.js`).

## Почему это важно

Для платформы, которую используют сторонние продавцы как "свой магазин",
визуальная и функциональная консистентность напрямую влияет на восприятие
профессионализма продукта их покупателями. Доступность — не только
соответствие стандартам, но и часть SEO (Lighthouse a11y score) и
расширение аудитории (пользователи с экранридерами, клавиатурная навигация).

## Что сделать

1. Задокументировать в `AGENTS.md` (или отдельном `docs/design-system.md`)
   разделение: `components/ui/*` — UI-механика (shadcn), `s-*` CSS-классы —
   бренд-токены магазина (цвет/фон/текст из `store_settings`). Любой новый
   код на витрине должен использовать существующие `s-*` классы, а не
   изобретать инлайн-стили заново (в `checkout/page.tsx` уже видно смешение:
   часть цветов через `style={{ backgroundColor: primaryColor }}`, часть
   через классы).
2. Пройтись по `cart/page.tsx`, `compare/page.tsx`, `profile/page.tsx`,
   `faq/page.tsx` тем же чек-листом, что был применён к `store/[slug]/page.tsx`
   в `_mobile_fix.js` — фиксированные grid/flex без responsive-модификаторов.
3. Заменить кликабельные `<div onClick>` на `<button>`/`<Link>` там, где они
   семантически являются интерактивными элементами.
4. Добавить `aria-label` на все icon-only кнопки (сердце, корзина, сравнение,
   избранное, переключатель темы).
5. Связать сообщения об ошибках форм с полями через `aria-describedby` +
   `aria-invalid` (React Hook Form это упрощает через `formState.errors`).
6. Прогнать Lighthouse accessibility audit на ключевых страницах витрины и
   дашборда, завести список найденного как чек-лист.

## Критерий готовности (DoD)

- [ ] Документ с разделением UI-механика / бренд-токены готов.
- [ ] Все интерактивные `<div>` заменены на семантические элементы.
- [ ] Все icon-only кнопки имеют `aria-label`.
- [ ] Lighthouse Accessibility score ≥ 90 на витрине и дашборде.
- [ ] Все страницы витрины проверены на мобильную адаптивность (не только
      главная страница каталога).
