# Шаг 11: Аналитика дашборда считается в браузере на полном наборе заказов

## Проблема

`app/dashboard/page.tsx` грузит **все** заказы магазина целиком
(`useSellerOrders(store?.id)` без пагинации/диапазона дат — см.
`lib/hooks/use-orders.ts:8-23`), а затем в `useMemo` (`dashboard/page.tsx:43+`)
на клиенте вручную фильтрует по периоду (`7d`/`30d`/`all`), считает выручку,
сравнивает с предыдущим периодом и строит данные для графика —
весь `reduce`/`filter` происходит в браузере поверх полного списка заказов.

Похожая клиентская агрегация встречается и на витрине: сортировка по
рейтингу/популярности в `store/[slug]/page.tsx` тоже происходит в памяти
после получения всех товаров, хотя сортировку можно сделать на уровне
запроса к БД.

## Почему это важно

Это не проблема, пока у магазина 50 заказов. Но это решение, которое не
масштабируется: при тысячах заказов каждый визит в дашборд будет тянуть
по сети весь массив заказов целиком (включая JOIN на `order_items` и
`products`, судя по `select("*, order_items(*, products(name, images))")`),
и пересчитывать аналитику в браузере на каждый рендер/смену периода.

## Что сделать

1. Перенести агрегацию выручки/количества заказов по периодам на сторону
   БД — либо через Postgres-функцию (`RPC`, по аналогии с уже существующей
   `increment_promo_usage`), либо через `supabase.from("orders").select(...)`
   с серверной фильтрацией по дате (`gte("created_at", periodStart)`) вместо
   загрузки всего и фильтрации в `useMemo`.
2. Для графика "выручка по дням/месяцам" — рассмотреть материализованное
   представление (`materialized view`) или агрегирующий RPC-запрос,
   считающий `sum(total_amount) group by date_trunc(...)` на стороне
   Postgres — на порядок быстрее, чем тянуть все заказы в JS.
3. Для сортировки товаров по рейтингу/популярности на витрине — выполнять
   `ORDER BY` на уровне запроса (потребует денормализованного поля
   `avg_rating`/`reviews_count` на `products`, обновляемого триггером при
   добавлении отзыва, раз рейтинг сейчас считается агрегацией на лету).
4. Добавить пагинацию/ограничение в `useSellerOrders`, если полный список
   заказов нужен где-то ещё (например, страница заказов в дашборде) —
   сейчас не проверено, используется ли там `LIMIT`.

## Критерий готовности (DoD)

- [ ] Запрос аналитики дашборда возвращает уже агрегированные данные, а не
      полный список заказов для пересчёта в браузере.
- [ ] Смена периода (7d/30d/all) не требует повторной загрузки всех заказов
      целиком.
- [ ] Сортировка товаров по рейтингу/популярности на витрине выполняется
      запросом к БД, а не `Array.sort` на клиенте.
- [ ] Дашборд остаётся быстрым (subjectively) при синтетическом тесте с
      несколькими тысячами заказов в тестовой БД.
