# Шаг 1: Заказ товара с вариантами падает на оформлении

## Проблема

Для товара с вариантами (цвет/размер и т.п.) `lib/store/cart-store.ts` и
`product-client.tsx` кладут в корзину **составной** `product_id`:

```ts
// app/store/[slug]/product/[id]/product-client.tsx:177-181
product_id:
  product.id +
  (Object.keys(selectedVariants).length > 0
    ? ":" + Object.values(selectedVariants).sort().join(",")
    : ""),
```

То есть в `cart-store` лежит строка вида `"3f1a...e2:Красный,L"`.

При оформлении заказа этот же `product_id` без какой-либо обработки
вставляется в БД:

```ts
// lib/hooks/use-orders.ts:93-98
const orderItems = input.items.map((item) => ({
  order_id: orderId,
  product_id: item.product_id,   // ← здесь та же составная строка
  quantity: item.quantity,
  price_at_time: item.price,
}));
```

А колонка `order_items.product_id` — это `UUID NOT NULL REFERENCES products(id)`
(`supabase/migrations/001_initial.sql:208`). Postgres не примет строку
`"3f1a...e2:Красный,L"` как UUID — insert упадёт с ошибкой
`invalid input syntax for type uuid`.

**Итог: любой заказ, где хотя бы один товар имеет выбранный вариант,
гарантированно не оформляется.** Заказ в `orders` уже создан (insert прошёл
раньше), а `order_items` — нет, то есть в БД остаётся заказ-сирота без
позиций.

## Почему это важно

Это не теоретический риск, а 100%-воспроизводимый баг в основном сценарии
покупки — для любого магазина, который использует варианты товаров (это
штатная фича, есть отдельная миграция `005_product_variants.sql`). Каждая
такая покупка — потерянный заказ и сломанный UX покупателя.

## Что сделать

Нужно разделить "идентификатор позиции в корзине" (уникальный для конкретной
комбинации товар+вариант, нужен только на клиенте для группировки/изменения
количества) и "ссылку на товар в БД" (должен быть настоящий UUID).

1. В `lib/store/cart-store.ts` добавить в `CartItem` поле
   `selectedVariants?: Record<string, string>` (или просто `variantKey: string`)
   и оставить `product_id` **настоящим** UUID товара.
2. Для уникальности строки корзины (чтобы разные варианты одного товара не
   схлопывались в одну позицию) использовать отдельное поле, например
   `lineId: string` (= `product_id + variantKey`), и матчить/удалять/обновлять
   количество по `lineId`, а не по `product_id`:
   - `addItem`, `removeItem`, `updateQuantity`, `getStoreItems` и т.д. в
     `cart-store.ts` сейчас сравнивают по `i.product_id === productId` —
     переключить на `lineId`.
3. В `product-client.tsx` передавать настоящий `product.id` как `product_id`,
   а собранную строку вариантов — отдельным полем `selectedVariants`/`variantLabel`.
4. В `checkout/page.tsx` и `use-orders.ts` (`useCreateOrder`) при формировании
   `order_items` использовать `item.product_id` (теперь уже настоящий UUID).
   Если нужно сохранить, какой именно вариант купили — добавить миграцию
   с колонкой `order_items.variant_label TEXT` (или `variant JSONB`), а не
   пытаться втиснуть это в `product_id`.
5. Проверить остальные места, где `cart-store` отдаёт `product_id` наружу
   (wishlist/compare не используют корзину, но стоит грепнуть `getStoreItems`
   по всему репозиторию на всякий случай).

## Критерий готовности (DoD)

- [ ] В корзину можно добавить два разных варианта одного товара — они не
      схлопываются в одну строку и не перетирают друг друга.
- [ ] Оформление заказа с товаром, у которого выбран вариант, проходит без
      ошибок, и в `order_items` лежит настоящий UUID товара.
- [ ] В заказе (дашборд продавца / история заказов покупателя) видно, какой
      именно вариант был куплен.
- [ ] Написан минимум один ручной/e2e тест: добавить в корзину товар с двумя
      разными вариантами → оформить заказ → заказ появился у продавца с
      правильными позициями.
